# Security Audit 2026-10

Date: 2026-10-23. Scope: Express/Prisma/Postgres backend. First run, no prior report. Read-only audit; no secret values are reproduced here.

## 1. Summary

Overall risk: **CRITICAL**

| Critical | High | Medium | Low | Info |
|---|---|---|---|---|
| 3 | 4 | 5 | 3 | 2 |

- Anyone on the internet can create an admin account (`POST /api/auth/register`) and can mint a valid JWT for any user id with no credentials (`GET /api/auth/refresh-token/:id`). Full read/write access to student personal data and medical notes follows.
- Production-style database credentials and a JWT seed were committed to git history (removed in 655c9db on 2026-03-10 but never rotated, as far as the repo shows).
- No rate limiting, no helmet, wildcard `*.vercel.app` CORS with credentials, no role checks anywhere, and `npm audit` reports 13 vulnerabilities (1 critical, 7 high) in production deps.

## 2. Changes since last report

First run: all findings are new. Still open: all. Resolved: none (`.env.production` and `.env.local` were untracked in 655c9db, which is a partial remediation; rotation not verifiable).

## 3. Findings

### SEC-2026-10-01 - Critical - Unauthenticated token minting for any user
- **Status (2026-10-27): fixed.** Route requires `validateJWT`; URL id must equal the authenticated user's id (403 otherwise).
- Location: `src/presentation/auth/routes.ts:36-38`, `src/presentation/services/auth.service.ts:70-88`, `src/presentation/auth/controller.ts:34-40`
- Issue: `GET /api/auth/refresh-token/:id` has no auth middleware and signs a fresh 2h JWT for whatever numeric user id is supplied, if the user exists.
- Exploit: `curl /api/auth/refresh-token/1` returns a valid token for user 1 (ids are sequential integers). Attacker then calls every protected endpoint.
- Fix: require `validateJWT` and derive the id from the verified token (`req.body.user.id`), never from the URL. Better: use a real refresh-token flow (separate long-lived opaque token, stored hashed, rotated).
- Effort: S

### SEC-2026-10-02 - Critical - Open admin registration
- **Status (2026-10-27): partly fixed.** `/register` now requires `validateJWT`; no role check, so any logged-in user can still create admins. Accepted risk, deferred with SEC-04.
- Location: `src/presentation/auth/routes.ts:25-34`, `src/presentation/services/auth.service.ts:16-39`
- Issue: `POST /api/auth/register` is public and always creates a user with `role: 'admin'`.
- Exploit: attacker registers, logs in, and has full access to all student data (including `asuntos_medicos`, phone, address), and can delete students/courses/events.
- Fix: remove the route or protect it with `validateJWT` plus a `super_admin` check; seed the first admin via a script.
- Effort: S

### SEC-2026-10-03 - Critical - Production DB credentials and JWT seed in git history
- **Status (2026-10-27): rotation done per maintainer** (production DB password changed, production `JWT_SEED` replaced; local dev seed was already different and never committed). Still to verify: DB host network exposure/IP restriction and DB access logs for unknown connections. History purge optional.
- Location: git history, commits ea08f7a (added), 0f6ceed and 655c9db (removed); files `.env.production`, `.env.local` (variables `DATABASE_URL`, `POSTGRES_URL`, `JWT_SEED`). Also `.env` (untracked, ignored) exists locally.
- Issue: `.env.production` contained a non-placeholder hosted-Postgres connection string with password and a `JWT_SEED`. Removing the file from HEAD does not remove it from history or any clone/fork.
- Exploit: anyone with repo read access (current or ever) can connect to the production DB directly or forge JWTs for any user id.
- Fix: rotate the DB password and `JWT_SEED` now (invalidates all sessions); verify the DB host is not publicly reachable or restrict by IP; if the repo is or was public, treat as breached and review DB access logs; optionally rewrite history with `git filter-repo`, but rotation is the real fix.
- Effort: S (rotate) / M (history purge)

### SEC-2026-10-04 - High - No role-based authorization on any route
- **Status (2026-10-27): open, deferred by maintainer** (all accounts are admins; not exploitable by outsiders).
- Location: all `routes.ts`; `Role` enum in `prisma/schema.prisma:11-14` is never checked (grep: no `role` use in middleware or services except register).
- Issue: every authenticated user, including self-registered ones, can delete students/courses/events/enrollments, edit any record, and change student `active`.
- Fix: add `AuthMiddleware.requireRole('super_admin')` for destructive and user-management endpoints (`DELETE /api/student/:id`, `/api/course/:id`, enrollment delete, event update/complete).
- Effort: M

### SEC-2026-10-05 - High - No brute-force protection, user enumeration on login
- **Status (2026-10-27): fixed.** Rate limit (10 per 15 min per IP) on login and register, generic "Invalid credentials", async bcrypt cost 12, 12-char minimum on register. Follow-up: set `trust proxy` once the host is known (SEC-09).
- Location: `src/presentation/auth/routes.ts:15-23`, `src/presentation/services/auth.service.ts:48,52`
- Issue: no rate limit or lockout; distinct messages "Email not exist in our records." vs "Password is invalid." Register also reveals "Email already exist". Password policy is min 6 chars. bcrypt uses `genSaltSync()` default cost 10 (`src/config/bcrypt.adapter.ts:5`) and sync calls block the event loop.
- Fix: `express-rate-limit` on `/api/auth/*`; single generic "Invalid credentials"; raise min length (12) ; use async `hash`/`compare` with cost 12.
- Effort: S

### SEC-2026-10-06 - High - Vulnerable production dependencies
- **Status (2026-10-27): fixed.** Dependencies upgraded; `npm audit --omit=dev` reports 0 vulnerabilities; build passes.
- Location: `package.json`, `package-lock.json`. `npm audit --omit=dev`: 13 vulns (1 critical, 7 high, 2 moderate, 3 low). See section 5.
- Fix: `npm audit fix` (run by the maintainer) then bump express 4.18.2 to 4.22.x, multer 2.2.0 to 2.5.0, express-validator to 7.3.x, jsonwebtoken 9.0.3, prisma/@prisma/client 6.19.x.
- Effort: S

### SEC-2026-10-07 - High - Internal error details returned to clients; register leaks hash
- **Status (2026-10-27): fixed.** Register strips `password_hash`; errors are logged server-side and a generic message is returned.
- Location: `src/presentation/services/auth.service.ts:33,37` and `:54`; `registerUser` returns `{user}` which is the full Prisma row including `password_hash` (only `loginUser` strips it).
- Exploit: the register response (and any 500 built as `` `${error}` ``, line 37) exposes the bcrypt hash / Prisma internals.
- Fix: strip `password_hash` in register (same destructure as login); return generic 500 messages and log server-side.
- Effort: S

### SEC-2026-10-08 - Medium - Wildcard CORS with credentials and `!origin` allowance
- **Status (2026-10-27): deferred by maintainer.**
- Location: `src/presentation/server.ts:36-52`, `src/config/envs.ts:11-13`
- Issue: any `https://*.vercel.app` (attacker-hosted Vercel site) and any `http://localhost:*` origin is allowed with `credentials: true`; requests with no Origin are allowed. Default origins include a specific preview deployment URL.
- Mitigating: auth is bearer-header based, not cookies, so CSRF risk is low; still unnecessary exposure.
- Fix: explicit allowlist from `CORS_ORIGINS` only; restrict localhost pattern to non-production; drop `credentials: true` unless cookies are used.
- Effort: S

### SEC-2026-10-09 - Medium - Missing HTTP hardening
- **Status (2026-10-27): fixed.** `helmet` (CSP off, CORP cross-origin), `x-powered-by` removed, global limit 600 per 15 min on `/api`, `trust proxy` driven by optional `TRUST_PROXY` env var (default 0). Set `TRUST_PROXY=1` in production behind a single proxy.
- Location: `src/presentation/server.ts:55-56`
- Issue: no `helmet`, `x-powered-by` enabled, `express.json()` with default 100kb limit (acceptable) but no rate limiting globally, no `trust proxy` setting (needed for correct client IPs once rate limiting is added), no HTTPS/HSTS enforcement.
- Fix: `app.disable('x-powered-by')`, `helmet()`, global rate limiter, `app.set('trust proxy', 1)` as appropriate for the host.
- Effort: S

### SEC-2026-10-10 - Medium - Upload hardening gaps (multer)
- **Status (2026-10-27): fixed** except magic-byte check and moving uploads out of `public/`. `validateJWT` runs before multer; only JPEG/PNG/WebP, extension derived from mimetype; `randomUUID` imported.
- Location: `src/config/multer.adapter.ts:4-25`, `src/presentation/courses/routes.ts:17,49`
- Issues: (a) filter trusts client-supplied `mimetype` and filename extension is preserved from `originalname`, so `evil.html` with `Content-Type: image/png` is stored under `public/images/` and served by `express.static`, enabling stored XSS on the API origin (and `.svg` is `image/svg+xml`, which passes `startsWith('image/')`); (b) multer runs BEFORE `validateJWT` on `POST /create` and `PUT /:id`, so unauthenticated users can write files to disk (up to 5MB each, disk-fill DoS); (c) uploaded files are never deleted on course update/delete (needs verification in `course.service.ts`); (d) `crypto.randomUUID()` used without an import (relies on the global; fine on Node 19+, needs verification on the deployed Node version).
- Fix: put `validateJWT` before multer; allowlist extensions (`.jpg/.jpeg/.png/.webp`) and derive the extension from the validated mimetype; verify magic bytes; serve uploads with `X-Content-Type-Options: nosniff`; store outside `public/` or on object storage.
- Effort: M

### SEC-2026-10-11 - Medium - Validation gaps, mass assignment, and IDOR-style scope
- **Status (2026-10-27): open, ignored by maintainer for now.**
- Location: `src/presentation/events/routes.ts:53-66` (PUT validators with no `fieldValidator` middleware, so validation results are never enforced); `src/presentation/enrollments/routes.ts:15-23` (validators never enforced: `fieldValidator` absent); `src/presentation/student/route.ts:49` (PUT has no validators; `req.body.first_name.trim()` throws on missing fields => 500); `student/controllers.ts:71` passes client `active`; `events/controllers.ts` and `courses/controllers.ts` pass `req.body` fields unvalidated to Prisma. `req.body.user` is overwritten by `validateJWT` so spoofing is not possible on protected routes, but a client may send arbitrary other body fields.
- Query params (`page`, `query`, `sortBy`) are not validated as scalar strings/ints in student/event/course controllers (type confusion with `?query[]=`); needs verification of each service. Report endpoints do clamp `limit` (<=100) correctly.
- IDOR: single-tenant admin model, so object-level checks are not applicable beyond the missing roles in SEC-04; flagged for awareness if multi-tenant is ever introduced.
- Fix: add `FieldValidatorMiddleware.fieldValidator` after the `check` chains, add `param('id').isInt()`, `query('page').optional().isInt({min:1})`, whitelist body fields.
- Effort: M

### SEC-2026-10-12 - Medium - Local DB defaults and prisma datasource env mismatch
- **Status (2026-10-27): open, ignored by maintainer for now.**
- Location: `docker-compose.yml` (user `postgres`, hardcoded weak password in file, port `5432:5432` bound to all interfaces, `restart: always`); `prisma/schema.prisma:7` uses `POSTGRES_URL` while `src/config/envs.ts:8` and `src/data/postgres/index.ts:7` use `DATABASE_URL`. Commit 980d25f also shows a historic weak local password in history (local dev only).
- Issue: the app runtime and migrations can silently point at different databases; superuser used for the app (needs verification for production).
- Fix: bind `127.0.0.1:5432:5432`, read the password from `.env`; unify on one variable name via `url = env("DATABASE_URL")`; use a least-privilege runtime DB role.
- Effort: S

### SEC-2026-10-13 - Low - `.env.template` incomplete / `.gitignore` gaps
- **Status (2026-10-27): open, ignored by maintainer for now.**
- `.env.template` lists only `PORT` and `CORS_ORIGINS`; missing `JWT_SEED`, `DATABASE_URL`, `API_URL` (required at boot per `envs.ts`). `.gitignore` covers `.env`, `.env.production`, `.env.local` but not other variants (`.env.*`); also no `uploads`/`security-reports` consideration (public/images contains tracked sample uploads, check they contain no personal photos).
- Fix: complete the template with placeholders; add `.env.*` and `!.env.template` to `.gitignore`.
- Effort: S

### SEC-2026-10-14 - Low - JWT hardening
- **Status (2026-10-27): open, ignored by maintainer for now.**
- Location: `src/config/jwt.adapter.ts:9-24`
- `algorithms` not pinned on verify (jsonwebtoken defaults are OK for HS256 secrets, but pin explicitly); no `iss/aud`; `JWT_SEED` has no minimum-length check in `envs.ts:6`; the token payload carries only the id (good); user is re-loaded from DB each request (good); no revocation or role in token. `decodeTokenExpiration` is called before the null-token check in login (`auth.service.ts:58-60`).
- Fix: `jwt.verify(token, secret, {algorithms:['HS256']})`, enforce `JWT_SEED` >= 32 chars, add issuer.
- Effort: S

### SEC-2026-10-15 - Low - Logging and privacy
- **Status (2026-10-27): open, ignored by maintainer for now.**
- Many `console.log(error)` sites (`auth.middleware.ts:34`, `student.service.ts` lines 289-628, `event.service.ts`, etc.). No request bodies or tokens logged directly, but Prisma errors can include query arguments containing personal data. Student list/search endpoints return email, phone, and (verify) address and `asuntos_medicos` (medical info) to all admins. No audit log for deletes, role or enrollment changes. No student data deletion/retention policy documented.
- Fix: structured logger with redaction; return minimal fields in list endpoints; audit table for destructive actions.
- Effort: M

### SEC-2026-10-16 - Info - Schema observations
- `prisma/schema.prisma`: no `onDelete` specified (default Restrict for required relations, so deleting a student with enrollments fails rather than cascading; verify the delete service handles that), no indexes beyond unique/PK on `Enrollments.student_id/event_id`, `Events.course_id`; `Users.password_hash` never selected in the API except via SEC-07. Latest migrations: `20260827185810_add_course_image_url`, two `20260912...make_gender_and_asuntos_medicos_optional` migrations (duplicate names, review for drift; `prisma migrate status` was not run since no local DB was confirmed).

### SEC-2026-10-17 - Info - Raw SQL and code execution scan clean
- No `$queryRaw`, `$executeRaw`, `eval`, `child_process`, `new Function` in `src/`. (`$executeRawUnsafe` with an interpolated password appears only in old history: 980d25f / 8530e56, a template artifact, since removed.)

## 6. Checks passed
- `git ls-files` includes only `.env.template` among env files; `.env` is ignored and not tracked; `dist/` and `/postgres/` ignored.
- `envs.ts` requires `JWT_SEED`, `DATABASE_URL`, `PORT`, `API_URL` with no secret defaults.
- JWT has 2h expiry, user is reloaded from DB per request, NaN id guarded, generic 401 messages.
- Login response strips `password_hash`; passwords hashed with bcrypt.
- No raw SQL, eval, child_process in current source; `res.sendFile` path is static (no user input).
- Multer has 5MB size limit, UUID filenames (no path traversal), image mimetype filter (weak, see SEC-10).
- Report endpoints clamp `limit` to 100; student/event pagination uses fixed page sizes.
- Current tracked `.env.template` contains only placeholders.

- Service-layer review was targeted (grep-based) rather than line-by-line for `student.service.ts`, `event.service.ts`, `enrollment.service.ts`; returned fields for `asuntos_medicos` and address need confirmation.
